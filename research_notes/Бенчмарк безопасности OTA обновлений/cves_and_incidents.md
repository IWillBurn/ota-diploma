# Known vulnerabilities in OTA / software-update implementations and major update-related attacks and failures (state as of 31 Oct 2026)

Method note: the CVE corpus was built by querying OSV.dev (`api.osv.dev/v1/query`) for the package ecosystems of the update clients (PyPI `tuf`, Go `go-tuf` / `go-tuf/v2`, crates.io `tough`, npm `tuf-js`, Packagist `php-tuf/php-tuf`, crates.io `tuf` (rust-tuf), Go `notation-go`, Go `sigstore-go`, Maven hawkBit, npm `electron-updater`, PyPI `pip`, etc.) and the NVD 2.0 API (keyword search plus lookup of individual CVE IDs). The queries ran on 31 Oct 2026. Project advisory pages (GitHub Security Advisories), vendor blogs and incident reports were then read directly. NVD/OSV publication dates are given as YYYY-MM-DD. Anything that could not be confirmed against a primary record is marked UNVERIFIED.

Legend for the root-cause class (column "Class"):
- **SIG**: signature, threshold or trust-chain verification bypass (duplicate keys, threshold = 0, unsigned or partly-signed content accepted, wrong certificate chain).
- **RB**: rollback / downgrade (an older, validly signed version is accepted).
- **FRZ**: freeze or stale metadata (expiry or validity period not checked).
- **MIX**: mix-and-match or wrong-target resolution (delegation order, the wrong artifact is verified).
- **PT**: path traversal / arbitrary file write (zip-slip, `../` in role or target names, symlinks).
- **MEM**: parser memory-safety bug (OOB read/write, integer over/underflow).
- **DOS**: DoS, endless data or resource exhaustion, panic or crash on malformed input.
- **TOCTOU**: race between verification and use.
- **KEY**: key handling (hard-coded or test keys, revocation, key-file permissions, crypto-design flaw).
- **TRANS**: insecure transport with no end-to-end authenticity (HTTP, no TLS, MITM).
- **ATOM**: missing atomicity or state-consistency bug (untrusted state persisted before validation; inconsistent slots or deployments).
- **AUTHZ**: access control in the server or a local service (not the cryptographic update path).

Legend for "Black-box detectable?":
- **MS**: detectable by a malicious repository, server or mirror (or a crafted artifact) against an unmodified client.
- **FI**: needs fault or race injection (power cut, file swap, I/O error, memory exhaustion).
- **FZ**: needs fuzzing of a parser or network input, usually with sanitizers.
- **LOCAL**: needs a co-resident local attacker or a configuration/permission audit; a plain network black box will not see it.
- **NO**: not detectable by a client-side black-box benchmark (build or maintainer compromise, crypto design, server-only).

This column is my own engineering assessment, made from each advisory's description. It is an inference, not something the sources state.

## Key question 1: CVE/GHSA corpus in update clients and servers, classified by attack class

### Takeaway
Since 2015 there have been dozens of advisories in the main open-source update frameworks (TUF clients, Notary/Notation, RAUC, SWUpdate, Mender, hawkBit, OSTree/Flatpak, MCUboot/Zephyr, U-Boot, GRUB) and in desktop/IoT updaters. Almost all of them are implementation bugs against designs that were themselves sound: duplicate-signature threshold counting, missing rollback or expiry checks, path traversal through role or target names, TOCTOU between verification and use, and integer overflows in parsers or in the code that computes the signed region. Many were reported in 2025–2026, so the problem is not shrinking. Most of the client-side cryptographic-path bugs could, in principle, be caught by a malicious-server or crafted-artifact black-box test.

### Inferences
- **Recurring classes across independent implementations.** Duplicate-signature threshold counting shows up in python-tuf (CVE-2020-6174), tough (CVE-2020-15093, and again in the delegated path in 2026 as CVE-2026-6966), go-tuf (GHSA-3633-5h82-39pq) and sigstore-go (CVE-2026-49834, per-log threshold). Path traversal through role or target names appears in python-tuf and tough at the same time (2021, same reporter), in go-tuf TAP 4 (2026), Flatpak (2026), pip, Sparkle and Notepad++ WinGUp. Missing rollback or expiry checks appear in go-tuf (2022), tough (2025, 2026), Notary v1 (2015) and Notation (2024). The TUF specification prevents all of these, so they support the thesis claim that the vulnerabilities live in implementations, not in specifications.
- **Signed-region and integer bugs.** RAUC CVE-2026-34155 (>2 GiB integer overflow, so the signature covers only a prefix) and U-Boot CVE-2026-46728 (hashed-nodes omitted from the hash) show a class a benchmark should probe directly: boundary sizes, and mutating bytes outside whatever the client actually hashes. Mender CVE-2025-67903 (an unlisted payload file bypasses verification) belongs to the same class.
- **TOCTOU in on-device installers** (RAUC 2020, SWUpdate 2025/2026, Zoom 2022, Squirrel.Mac 2026, Tesla gateway 2023) needs a fault- or race-injection harness, such as a co-resident process swapping files between verification and use. A pure malicious-server test will miss this class.
- **Regressions are a distinct sub-class.** GRUB CVE-2021-3418 is "a reintroduction of CVE-2020-15705". tough CVE-2026-6966 repeats CVE-2020-15093 in delegated roles. Windows CVE-2024-43491 is a servicing-stack update that rolled back earlier fixes. All three are caught only if the attack tests are re-run on every release, which supports an executable benchmark over one-off audits.
- **Parser differentials** (one parser validates, another installs) recur: Android Master Key (duplicate ZIP entries, 2013), Flatpak NUL-byte metadata (2022), pip tar+ZIP polyglot (2026). They suggest a benchmark test class of "polyglot or duplicate-entry artifacts".
- **Rough tally of the black-box column** (my count over the roughly 120 IDs above): about 60–65% are detectable by a malicious server or crafted artifact (MS), about 15% need parser fuzzing (FZ), about 10% need fault or race injection, and the rest are LOCAL, server-side AUTHZ or NO. This tally is approximate and should be recomputed if the table is used for statistics in the thesis.
- **Fix quality.** Fixes are themselves fragile. Supermicro's BMC signature fix was bypassed twice (2025, 2026). The tough threshold bug returned in delegated roles six years after the first fix. Zoom's first fix was bypassed within days. This argues for keeping regression suites (benchmarks) executable rather than relying on one-off audits.

### Gaps
- MCUboot GHSA-gcxh-546h-phg4 and GHSA-8hrv-4cp5-4rg3: the CVE IDs and fixed versions were not visible on the advisory list page, and OSV returned no record for these GHSA IDs.
- No Android-OTA-specific (update_engine / A/B OTA / recovery) CVEs were researched in depth. Only the APK-level signature bypasses CVE-2013-4787 and CVE-2017-13156 are included (table E).
- The U-Boot/Barebox CVE IDs from Microsoft's March 2025 bootloader research could not be mapped with certainty. "CVE-2025-26721…26729" is not in NVD.
- No CVEs were found for aktualizr, ota-tuf, Uptane reference implementations, tuf-js, rust-tuf or php-tuf. This is "none found in OSV/NVD", not proof of absence.
- Clear Linux `swupd`: no CVE found.
- Windows Update CVE-2024-38202 fix date: a secondary source (ReversingLabs, via search) says October 2024 Patch Tuesday. UNVERIFIED against the Microsoft MSRC page.
- CVSS scores were deliberately not tabulated, because aggregators disagree (e.g., tough CVE-2025-2885: 4.2 / 4.5 / 5.7 depending on source and CVSS version).

## Key question 2: Bugs found by tuf-conformance or by differential testing between TUF clients

### Takeaway
There is documented, primary-source evidence that the executable TUF conformance suite found real security bugs in production clients: go-tuf CVE-2024-47534 and the tough 2025 batch (CVE-2025-2885, -2886, -2887, -2888 and GHSA-j8x2-777p-23fc). This is the closest existing precedent for the thesis's "executable cross-ecosystem benchmark". Cross-implementation discovery (one reporter finding the same bug class in python-tuf and tough) is also documented.

### Cited Findings
- tuf-conformance is "a conformance test suite for TUF clients". Its goals are to "measure the clients conformance with the TUF specification", achieve "better practical compatibility with other implementations" and collaborate on tests. A client is wrapped in a CLI executable implementing the "client-under-test CLI protocol" (CLIENT-CLI.md), run via a GitHub Action, and may list unsupported optional features in an `<entrypoint>.xfails` file. The repository ships two client-under-test implementations (python-tuf and go-tuf Makefile targets) — [tuf-conformance README](https://github.com/theupdateframework/tuf-conformance).

The test was `test_graph_traversal` in tuf-conformance PR #115. Fixed in go-tuf/v2 2.0.1 — [GHSA-4f8r-qqr9-fq8j](https://github.com/theupdateframework/go-tuf/security/advisories/GHSA-4f8r-qqr9-fq8j), [NVD](https://nvd.nist.gov/vuln/detail/CVE-2024-47534).

Finders are jku (Jussi Kukkonen) and AdamKorcz, and Google is thanked for coordinated disclosure. All five tough advisories of 28 Mar 2025 were fixed in 0.20.0 — [GHSA-5vmp-m5v2-hx47](https://github.com/awslabs/tough/security/advisories/GHSA-5vmp-m5v2-hx47), [GHSA-76g3-38jv-wxh4](https://github.com/awslabs/tough/security/advisories/GHSA-76g3-38jv-wxh4).

- Cross-implementation discovery: jku reported the role-name path traversal in tough (CVE-2021-41150) and target-name traversal (CVE-2021-41149) alongside python-tuf's CVE-2021-41131 (same date, 2021-10-19). The tough advisory references the python-tuf advisory — [GHSA-r56q-vv3c-6g9c](https://github.com/awslabs/tough/security/advisories/GHSA-r56q-vv3c-6g9c), [GHSA-wjw6-2cqr-j4qr](https://github.com/theupdateframework/python-tuf/security/advisories/GHSA-wjw6-2cqr-j4qr).

- Audits as another discovery channel: X41 D-Sec's audit of python-tuf (announced 26 Oct 2022) found "one medium and four low-severity issues" — [OSTIF](https://ostif.org/our-audit-of-python-tuf-is-complete-multiple-issues-found-and-fixed/). Quarkslab's audit of notation-go found CVE-2024-56138 and CVE-2024-51491 — [NVD 56138](https://nvd.nist.gov/vuln/detail/CVE-2024-56138), [NVD 51491](https://nvd.nist.gov/vuln/detail/CVE-2024-51491).
- In 2026, independent researchers (1seal; Oxide Computer) reported further go-tuf and tough bugs (CVE-2026-23991 panic-before-verify; CVE-2026-6966 delegated duplicate signatures). The advisories do not say how they were found — [GHSA-846p-jg2w-w324](https://github.com/theupdateframework/go-tuf/security/advisories/GHSA-846p-jg2w-w324), [GHSA-8m7c-8m39-rv4x](https://github.com/awslabs/tough/security/advisories/GHSA-8m7c-8m39-rv4x).

### Inferences
- At least 6 security advisories (1 in go-tuf, 5 in tough) are publicly attributed to tuf-conformance. Every one is a *specification-workflow* bug (delegation order, terminating delegations, sequential root versions, delegated rollback, cache persistence order, cycles), i.e. exactly what a malicious-repository black-box scenario exercises. That gives an empirical precedent for the thesis's methodology. The thesis can position itself as generalizing tuf-conformance beyond TUF (to RAUC, SWUpdate, Mender, MCUboot and others) and adding fault injection and fuzzing.
- The 2026 recurrence in tough (delegated-path duplicate signatures, delegated metadata missing checks) suggests conformance tests had covered top-level roles more thoroughly than delegated ones. A benchmark should apply each attack to every role or path in which the check must be repeated.

### Gaps
- I could not find a blog post by Jussi Kukkonen or OpenSSF quantifying the total number of tuf-conformance findings, nor a public "Client Conformance Report" snapshot with pass/fail per client. The README mentions such a report but its contents were not retrieved.
- The tuf-js and rust-tuf results under tuf-conformance were not found.
- No academic differential-testing paper across TUF clients was found in this pass.

## Key question 3: Landmark incidents (update channel as an attack vector, and outages or bricking from faulty updates), with verified facts

### Takeaway
Update channels have been used repeatedly to compromise thousands to millions of systems: SolarWinds, NotPetya, ShadowHammer, CCleaner, Kaseya, 3CX, Notepad++, eScan and AOMEI. Faulty updates without staged rollout or validation caused the largest IT outage on record (CrowdStrike, 8.5M Windows devices) and repeated vehicle and IoT bricking (Rivian 2023, Jeep 4xe 2025 recall of 24,238 vehicles, FCA Uconnect 2018, LockState 2017). In most attack cases the malicious update was *validly signed* (build or signing compromise). Where it was not (Notepad++ before 8.8.9, eScan 2019–2023, AOMEI 2026), the updater lacked end-to-end signature verification.

### Cited Findings

#### 3a. Attacks delivered through the update channel

- **SolarWinds Orion / SUNBURST (disclosed 13 Dec 2020).** The trojanized `SolarWinds.Orion.Core.BusinessLayer.dll` was "a digitally signed component". "Multiple trojanized updates were digitally signed from March - May 2020 and posted to the SolarWinds updates website" (e.g., `SolarWinds-Core-v2019.4.5220-Hotfix5.msp`). It had a dormant period "of up to two weeks", and the campaign "may have begun as early as Spring 2020" — [Mandiant/FireEye](https://cloud.google.com/blog/topics/threat-intelligence/evasive-attacker-leverages-solarwinds-supply-chain-compromises-with-sunburst-backdoor). SolarWinds' 8-K (14 Dec 2020): about 33,000 Orion customers were notified, and "fewer than 18,000" may have installed affected builds — [SEC 8-K](https://www.sec.gov/Archives/edgar/data/1739942/000162828020017451/swi-20201214.htm).
- **NotPetya via M.E.Doc (27 Jun 2017).** ESET found a backdoor in `ZvitPublishedObjects.dll` shipped in at least three official updates: 10.01.175–176 (14 Apr 2017), 10.01.180–181 (15 May) and 10.01.188–189 (22 Jun). The backdoor used M.E.Doc's "regular update check requests to the official M.E.Doc server upd.me-doc.com[.]ua", exfiltrating data in cookies. The outbreak (DiskCoder.C) came on 27 Jun 2017, five days after the last update. ESET "assume[s] that the attackers had access to the M.E.Doc application source code" — [ESET WeLiveSecurity](https://www.welivesecurity.com/2017/07/04/analysis-of-telebots-cunning-backdoor/). Cisco Talos (on-site) confirmed delivery via the M.E.Doc update system — [BankInfoSecurity](https://www.bankinfosecurity.com/notpetya-patient-zero-ukrainian-accounting-software-vendor-a-10080).
- **ASUS Live Update / ShadowHammer (Jun–Nov 2018, disclosed Mar 2019).** "The trojanized updaters were signed with legitimate certificates" and "hosted on the official liveupdate01s.asus[.]com and liveupdate01.asus[.]com ASUS update servers". Over 57,000 Kaspersky users installed it, with an estimated "over a million users worldwide". Over 600 unique target MAC addresses were extracted from more than 200 samples, and ASUS was notified on 31 Jan 2019 — [Kaspersky Securelist](https://securelist.com/operation-shadowhammer/89992/). ASUS fixed it in Live Update 3.6.8 — [PC Gamer](https://www.pcgamer.com/asus-unwittingly-pushed-out-malware-to-57000-pcs-security-firm-says).
- **CCleaner (Aug–Sep 2017).** The validly signed CCleaner v5.33.6162 and CCleaner Cloud v1.07.3191 were backdoored. Avast estimated 2.27M users of 5.33.6162 and 5,010 Cloud users. The release went out on 15 Aug and was downloadable until 12 Sep, and Talos notified Avast on 13 Sep 2017 — [Dark Reading](https://www.darkreading.com/application-security/avast-ccleaner-compromised-amid-rise-in-supply-chain-threats), [The Register](https://www.theregister.com/2017/09/18/tainted_ccleaner_downloads). Avast disputes that Talos found it first — [Computing](https://computing.co.uk/news/3017604/avast-cisco-talos-didnt-discover-ccleaner-compromise-first).
- **Kaseya VSA / REvil (2 Jul 2021).** On-premises VSA servers were exploited via zero-day(s), with CVE-2021-30116 reported by DIVD in April 2021 (researchers name CVE-2021-30116/30119/30120 as candidates). Ransomware was then pushed to managed endpoints. Kaseya counted fewer than 60 direct customers and about 1,500 downstream businesses, and patched on 11 Jul 2021 — [The Record](https://therecord.media/kaseya-more-than-1500-downstream-businesses-impacted-by-ransomware-attack), [Security Affairs](https://securityaffairs.com/119759/cyber-crime/kaseya-attack-impacted-1500-businesses.html). NVD: CVE-2021-30116 means "Kaseya VSA before 9.5.7 allows credential disclosure, as exploited in the wild in July 2021", via the client download page and the generated `KaseyaD.ini` (CWE-522) — [NVD](https://nvd.nist.gov/vuln/detail/CVE-2021-30116). The precise abuse of VSA's agent-update or procedure mechanism to push the ransomware was not verified from a primary source (UNVERIFIED).
- **3CX DesktopApp (Mar 2023; Mandiant report 20 Apr 2023).** UNC4736 (suspected DPRK). The initial vector was a trojanized `X_TRADER_r7.17.90p608.exe`, signed with a Trading Technologies certificate "set to expire in October 2022" and still downloadable in 2022. The attackers compromised both the Windows and macOS build environments, and 3CX DesktopApp 18.12.416 and earlier was affected. "This is the first time Mandiant has seen a software supply chain attack lead to another software supply chain attack" — [Mandiant](https://cloud.google.com/blog/topics/threat-intelligence/3cx-software-supply-chain-compromise). CVE-2023-29059 (NVD, 30 Mar 2023) covers Windows Electron app 18.12.407 and 18.12.416 ("Update 7") and macOS 18.11.1213, 18.12.402, 18.12.407 and 18.12.416 — [NVD](https://nvd.nist.gov/vuln/detail/CVE-2023-29059).
- **tj-actions/changed-files, CVE-2025-30066 (14–15 Mar 2025).** This is a CI/CD "update" channel: the mutable version tags v1–v45.0.7 "were modified by a threat actor to point at commit 0e58ed8", which leaked secrets into Actions logs. Consumers who pinned a tag instead of a hash silently received the malicious version — [NVD](https://nvd.nist.gov/vuln/detail/CVE-2025-30066). It is relevant to the thesis as a mix-and-match / unauthenticated-reference failure (a tag resolved without a signed snapshot).
- **xz-utils backdoor, CVE-2024-3094 (29 Mar 2024).** Andres Freund posted on oss-security that xz 5.6.0 and 5.6.1 were affected. The `build-to-host.m4` trigger was present only in release tarballs, but "the files containing the bulk of the exploit are in an obfuscated form committed upstream". The backdoor reaches sshd via libsystemd, works only on glibc, and targets x86-64. It was discovered through slow ssh logins (0.299 s → 0.807 s) and valgrind errors — [oss-security](https://www.openwall.com/lists/oss-security/2024/03/29/4), [NVD](https://nvd.nist.gov/vuln/detail/CVE-2024-3094).
- **Polyfill.io (Sansec, 25 Jun 2024).** "In February this year, a Chinese company bought the domain and the Github account". Over 100K sites embedded `cdn.polyfill.io`. The injected code redirected mobile users to betting sites through the fake domain `googie-anaiytics.com`, and it "only activates on specific mobile devices at specific hours", not for admin users — [Sansec](https://sansec.io/research/polyfill-supply-chain-attack). The buyer is identified as Funnull and Cloudflare estimated "tens of millions" — [BleepingComputer](https://www.bleepingcomputer.com/news/security/polyfillio-javascript-supply-chain-attack-impacts-over-100K-sites/) (secondary).
- **eScan / GuptiMiner (reported Apr 2024).** Attackers in a MITM position swapped eScan's HTTP update packages for backdoors and miners. eScan confirmed the fix on 31 Jul 2023, and Avast noted possible Kimsuky links — [Avast/Gen Digital](https://gendigital.com/blog/insights/research/guptiminer-hijacking-antivirus-updates-for-distributing-backdoors-and-casual-mining), [Security Affairs](https://securityaffairs.com/162228/breaking-news/escan-antivirus-mitm-attack.html).
- **Notepad++ / WinGUp hijack (Jun–Dec 2025; disclosed early Feb 2026).** Per the official incident page, "The incident began in June 2025". The shared hosting server was "compromised until the 2nd of September, 2025", but attackers "maintained the credentials of our internal services" until 2 Dec 2025. Update traffic from *selected* targets was redirected to attacker manifests via `getDownloadUrl.php`. From v8.8.9, WinGup verifies the installer's certificate and signature and the update XML is XMLDSig-signed, with enforcement from v8.9.2. Attribution: "likely a Chinese state-sponsored group" — [Notepad++ official](https://notepad-plus-plus.org/news/hijacked-incident-info-update/). The CVE is CVE-2025-15556 (published 3 Feb 2026) — [NVD](https://nvd.nist.gov/vuln/detail/CVE-2025-15556). Early press said "no CVE has been assigned", which is now outdated. Secondary: a backdoor named "Chrysalis" and attribution to Zirconium/Violet Typhoon by Kevin Beaumont — [Help Net Security](https://www.helpnetsecurity.com/2026/02/02/2025-notepad-supply-chain-compromise/), [Orca](https://orca.security/resources/blog/notepad-plus-plus-supply-chain-attack/) (UNVERIFIED beyond these secondary sources).
- **eScan update-server compromise (20 Jan 2026).** A regional update-server configuration was accessed, and a "corrupt" update was served for about 2 hours. The malicious `Reload.exe` modified the hosts file and registry to block further eScan updates. MicroWorld and Morphisec dispute the scope and who discovered it first, and how access was gained is unknown — [Help Net Security](https://www.helpnetsecurity.com/2026/01/29/escan-antivirus-update-supply-chain-compromised/), [The Register](https://www.theregister.com/2026/01/29/escan_morphisec_dispute/). A report that the packages were signed with a compromised eScan certificate comes from secondary coverage (UNVERIFIED).
- **AOMEI Backupper and AnyViewer "ephemeral tampering" (Apr–Jul 2026; GTIG report 15 Oct 2026).** UNC7017 modified the vendor-hosted `down_html.ini` (version, **MD5 of the expected package**, download URL) and `Notifycfg.ini` for only 10, 6 and 5 minutes (28 May, 16 Jul, 20 Jul 2026, UTC). The attacker pointed the URL to an attacker host and substituted a matching MD5, and the notification flow executed CROSSROAD, which led to SHINYROAD (Radmin-based backdoor) and Adaptix C2. GTIG: "Update clients should never rely solely on transport-layer HTTPS or remote checksums (such as cleartext MD5 values in an unauthenticated configuration file)". "Organizations running AOMEI software cannot assume they are protected solely because the vendor took corrective server-side action." Mandiant notified AOMEI on 17 Jul 2026 — [Google GTIG/Mandiant](https://cloud.google.com/blog/topics/threat-intelligence/investigating-ephemeral-supply-chain-tampering), [BleepingComputer](https://www.bleepingcomputer.com/news/security/hackers-hijack-aomei-update-servers-to-secretly-spread-malware/).
- **Historical baseline: package managers (2008).** Cappos, Samuel, Baker and Hartman studied ten package managers and found that all "have vulnerabilities that can be exploited by a man-in-the-middle or a malicious mirror". They estimated that "an attacker with a mirror can compromise or crash hundreds to thousands of clients weekly", and they defined replay, freeze and endless-data attacks — [CCS 2008 paper (PDF)](https://www2.cs.arizona.edu/stork/packagemanagersecurity/ccs2008.pdf), [LWN summary](https://lwn.net/Articles/327847).

#### 3b. Outages and bricking caused by faulty updates (fault-tolerance side)

- **CrowdStrike Falcon Channel File 291 (19 Jul 2024).** The content update was released at 04:09 UTC and reverted at 05:27 UTC. It affected Windows sensors 7.11+ that were online in that window, and Mac and Linux were not affected — [CrowdStrike PIR](https://www.crowdstrike.com/en-us/blog/falcon-content-update-preliminary-post-incident-report/). Microsoft: "We currently estimate that CrowdStrike's update affected 8.5 million Windows devices", which is less than 1% of Windows machines (David Weston, 20 Jul 2024) — [Microsoft blog](https://blogs.microsoft.com/blog/2024/07/20/helping-our-customers-through-the-crowdstrike-outage/), [TechCrunch](https://techcrunch.com/2024/07/20/microsoft-says-8-5m-windows-devices-were-affected-by-crowdstrike-outage/).
  - RCA (6 Aug 2024): "The new IPC Template Type defined 21 input parameter fields, but the integration code that invoked the Content Interpreter with Channel File 291's Template Instances supplied only 20". Testing used wildcard matching for the 21st field. The new instance with a non-wildcard criterion for the 21st input produced "an out-of-bounds read of the input array" ("not an arbitrary memory write"), and "The Content Validator contained a logic error".
  - The RCA findings include: no compile-time validation of the field count, a missing runtime bounds check, insufficient test variety, the Validator logic error, no Interpreter-in-the-loop testing of template instances, and "Template Instances should have staged deployment" — [CrowdStrike External Technical RCA (PDF)](https://www.crowdstrike.com/wp-content/uploads/2024/08/Channel-File-291-Incident-Root-Cause-Analysis-08.06.2024.pdf).
  - Committed fixes: "a staggered deployment strategy for Rapid Response Content" starting with canary, and customer control over delivery — [CrowdStrike PIR](https://www.crowdstrike.com/en-us/blog/falcon-content-update-preliminary-post-incident-report/).
- **Cloudflare (18 Nov 2025).** The failure started at 11:20 UTC. A ClickHouse permissions change made the Bot Management "feature file" about double in size (duplicate rows). It was pushed network-wide every few minutes, exceeded a hard-coded 200-feature limit (normal use is about 60) and caused proxy panics. Full recovery came at 17:06 UTC. Remediation: validate internally generated configuration files like user input — [Cloudflare post-mortem](https://blog.cloudflare.com/18-november-2025-outage/), [ilert summary](https://www.ilert.com/postmortems/cloudflare-global-outage-nov-2025). The 200/60 and 17:06 figures come from secondary summaries; verify against the Cloudflare post before quoting.
- **Google Cloud (12 Jun 2025).** A Service Control quota-policy code path added on 29 May 2025 had no feature flag or error handling. A policy with blank fields, replicated globally via Spanner, caused crash loops in all regions, and the "red button" took about 40 minutes — [ByteByteGo](https://blog.bytebytego.com/how-the-google-cloud-outage-crashed), [Cybersecuritynews](https://cybersecuritynews.com/google-massive-cloud-outage-linked/amp/). These are secondary; Google's own incident report (dated 14 Jun 2025) was not retrieved, so UNVERIFIED in detail.
- **Rivian 2023.42 OTA (Nov 2023).** Rivian's software VP: "a fat finger where the wrong build with the wrong security certificates was sent out". Infotainment screens went black at 90% install, the campaign was cancelled, and a remote fix rolled out from 15 Nov. Some vehicles needed physical service — [InsideEVs](https://insideevs.com/news/696177/rivian-ota-update-softbricks-evs/), [The Register](https://www.theregister.com/2023/11/15/rivian_bricked_infotainment_systems/). The figure of 1,463 affected vehicles in NHTSA filings is from search-summary secondary reporting (UNVERIFIED).
- **Jeep Wrangler 4xe OTA (10 Oct 2025).** A Uconnect/telematics OTA caused incomplete communication between the Telematics Box Module and the Hybrid Control Processor. The HCP reset, causing loss of drive power, in some cases at highway speed. NHTSA recall **25V710** (FCA campaign A7C), filed 17 Oct 2025, covers **24,238** MY2023–2025 Wrangler 4xe built 21 Feb 2023 – 5 Jun 2025 — [NHTSA recall report (PDF)](https://static.nhtsa.gov/odi/rcl/2025/RCLRPT-25V710-7238.pdf), [Fox13](https://www.fox13news.com/news/chrysler-recall-jeeps-potential-loss-drive-power), [Jalopnik](https://www.jalopnik.com/1996500/jeep-hybrids-bricked-after-ota-software-update/).
- **FCA Uconnect reboot loop: February 2018, not 2023.** An OTA released on 9 Feb 2018 put 2017–2018 Uconnect 8.4" units into reboot loops every 30–45 s. It was tied to the SiriusXM Travel Link service, and FCA shut the service down for 48 h — [The Drive](https://www.thedrive.com/tech/18454/an-over-the-air-update-is-causing-fca-uconnect-systems-to-endlessly-reboot), [Jalopnik](https://jalopnik.com/1822941299). No 2023 Uconnect bricking event was found; the only Feb 2023 item is an NHTSA TSB on radio OTA (blank screen, battery drain).
- **LockState / RemoteLock 6i (Aug 2017).** Firmware for 7000i locks was pushed to 6000i units. The locks could not reconnect, so they could not be fixed OTA. About 500 locks were affected, about 200 belonging to Airbnb hosts, and repair meant shipping the lock back or getting a replacement — [BleepingComputer](https://www.bleepingcomputer.com/news/hardware/botched-firmware-update-bricks-hundreds-of-smart-door-locks), [Threatpost](https://threatpost.com/smart-locks-bricked-by-bad-update).
- **HP OfficeJet Pro 9020e series (May 2023).** An auto-installed firmware update bricked printers with error 83C0000B, and service or replacement was required — [Engadget](https://www.engadget.com/hp-officejet-printers-are-bricking-following-a-recent-software-update-223559237.html), [PCWorld](https://www.pcworld.com/article/1925926/an-hp-firmware-update-is-bricking-printers-and-theres-no-fix-yet.html).
- **Garmin "blue triangle" boot loop (28 Jan 2025).** Many watch and Edge models boot-looped after a file pushed on sync, reportedly a faulty GPS-related CPE file. Treat as UNVERIFIED.

### Inferences
- Two different failure modes map onto the two halves of the thesis benchmark:
  - **Security:** a malicious update reaching clients. It was signed in SolarWinds, ShadowHammer, CCleaner, 3CX and M.E.Doc, so client-side verification could not help there. It was unsigned or weakly verified in Notepad++ <8.8.9, eScan (HTTP) and AOMEI (MD5 from the same unauthenticated channel), and correct end-to-end verification (TUF-style) would have blocked those.
  - **Fault tolerance:** a valid but faulty update. CrowdStrike, Cloudflare and Google Cloud lacked staged rollout, input validation or a kill switch. Rivian, LockState, Jeep and HP lacked target/compatibility checks or recoverability.
- AOMEI 2026 is a textbook example of why a hash fetched from the same channel as the payload is not integrity protection. It maps directly to a benchmark test: "server returns a matching hash for a substituted artifact".
- The short tampering windows in AOMEI (5–10 min) and eScan (about 2 h) mean that detection by repository-side monitoring is hard. Client-side verification is the only robust control, which strengthens the thesis's client-focused benchmark.

### Gaps
- NotPetya total damage (often quoted as about $10 billion) was not verified against a primary source in this pass (UNVERIFIED).
- The Kaseya VSA delivery mechanism (abuse of the agent-update or procedure feature) is not confirmed from a Kaseya/CISA primary source. CVE-2021-30116 itself is confirmed in NVD as credential disclosure.
- The Rivian NHTSA count (1,463) is UNVERIFIED.
- The Google Cloud 12 Jun 2025 official incident report was not retrieved.
- Other notable 2025–2026 OTA bricking incidents (e.g., other EV makers) were not systematically searched beyond those listed.

## Key question 4: Statistics on update-channel and supply-chain attacks

### Takeaway
Quantitative reports agree that supply-chain and third-party vectors are large and growing. ENISA (2021) found that 66% of analysed supply-chain attacks targeted supplier code. Verizon DBIR 2025 found that third-party involvement doubled to 30% of breaches. Sonatype counted over 454,600 new malicious open-source packages in 2025 alone. None of these reports isolates "OTA/update-client" attacks as a separate category, so the thesis should cite them as context, not as a measure of OTA-specific risk.

### Cited Findings
- ENISA *Threat Landscape for Supply Chain Attacks* (July 2021): analysed 24 attacks from Jan 2020 to early Jul 2021. In 66% the attackers focused on the supplier's code; about 62% of attacks on customers exploited their trust in the supplier; 62% used malware; about 42% were unattributed. Some coverage also uses "66%" for suppliers not knowing or not reporting how they were compromised, so check which metric is meant — [ENISA report](https://enisa.europa.eu/publications/threat-landscape-for-supply-chain-attacks/@@download/fullReport), [Trend Micro summary](https://trendmicro.com/en_us/research/21/h/most-supply-chain-attacks-target-suppliers-code-enisa.html). ENISA predicted a fourfold increase in supply-chain attacks in 2021 — [CPO Magazine](https://www.cpomagazine.com/cyber-security/enisa-predicts-fourfold-increase-in-software-supply-chain-attacks-in-2021-warning-that-strong-cyber-defenses-were-no-longer-effective/).
- Sonatype *2026 State of the Software Supply Chain* (2025 data): "more than 454,600 new malicious packages" in 2025, bringing the cumulative total of known and blocked malware to over 1.233 million (npm, PyPI, Maven Central, NuGet, Hugging Face) — [Sonatype](https://sonatype.com/state-of-the-software-supply-chain/2026/open-source-malware), [ITPro](https://www.itpro.com/software/open-source/the-open-source-ecosystem-is-booming-thanks-to-ai-but-hackers-are-taking-advantage). Quarterly index: 17,954 (Q1 2025) — [Sonatype press release](https://www.sonatype.com/press-releases/18000-new-malicious-packages-discovered-in-q1).
- Verizon DBIR 2025: third-party involvement in breaches rose from 15% to 30%. The dataset covers 22,052 incidents and 12,195 breaches (1 Nov 2023 – 31 Oct 2024) — [Verizon](https://verizon.com/about/news/2025-data-breach-investigations-report), [The Register](https://www.theregister.com/2025/04/24/security_snafus_third_parties/).
- Cappos et al. (CCS 2008): 10 of 10 package managers studied were vulnerable to a MITM or malicious mirror — [paper](https://www2.cs.arizona.edu/stork/packagemanagersecurity/ccs2008.pdf).
- PKfail: Binarly's pk.fail scanner flagged 791 firmware releases, about an 8.5% vulnerability rate among scanned images — [TechSpot](https://www.techspot.com/news/104776-pkfail-security-flaw-far-more-extensive-than-initially.html).

### Inferences
- Own corpus (Key question 1): at least 18 advisories in 2026 alone across RAUC, SWUpdate, Mender, hawkBit, Zephyr, MCUboot, U-Boot, Flatpak, go-tuf, tough, sigstore-go, Sparkle, Notepad++ and electron-updater consumers. That is evidence the problem is current, not historical. It is my count from the tables and should be recomputed if cited.

### Gaps
- No report was found that quantifies *update-mechanism-specific* attacks (as opposed to general supply-chain or third-party attacks). An "update hijack incidents per year" statistic would have to be compiled by the thesis author from the incident list above.
- ENISA has not published a successor supply-chain-specific report with comparable numbers (not checked in this pass).
