# Протокол адаптера otabench

Чтобы стенд испытал реализацию, ему нужен адаптер: небольшое описание того, как реализацию
запустить и как узнать её состояние. Код самой реализации стенд не читает и не импортирует.
Язык и способ сборки не важны: годится и готовый бинарник. Вердикт выносится по внешним
наблюдениям: что лежит на диске, что клиент принял, с какого слота загрузилось устройство.

Уровней два:

| Уровень | Что испытывается | Адаптер | Где |
|---|---|---|---|
| **v1, клиент** | библиотека или клиент обновления метаданных (TUF) | исполняемый файл с командами `init / refresh / download` | `bench/clients.yaml`, `bench/otabench/adapter.py` |
| **v2, устройство** | A/B-апдейтер целиком: запись слота, загрузчик, подтверждение | YAML-файл с командами, которые выполняются в госте | `bench/updaters/<имя>.yaml`, `bench/otabench/device.py` |

## v1: клиент

Совпадает с протоколом tuf-conformance (`third_party/tuf-conformance/CLIENT-CLI.md`), поэтому
любой клиент, уже подключённый к tuf-conformance, подключается к otabench без изменений.

```
<client> --metadata-dir D init ROOT
<client> --metadata-dir D --metadata-url U refresh
<client> --metadata-dir D --metadata-url U --target-name N --target-base-url T --target-dir TD download
```

Код 0 — успех, 1 — любая ошибка. Вердикт стенд выносит не по коду возврата, а по содержимому
`D` и `TD` и по поведению клиента на стороне сервера (п. 2.3 ВКР).

Запись в `clients.yaml`: `name`, `spec`, `version`, `command` (плейсхолдеры `{python}`,
`{node}`, `{root}`), необязательные `env` и `path_prepend`.

## v2: устройство

Адаптер — это один YAML-файл. Стенд запускает образ в QEMU и выполняет команды адаптера в госте
через qemu-guest-agent как `/bin/sh -c <команда>`. Сеть гостю для этого не нужна. Сценарии
(`bench/scripts/pilot_ab.py`) обращаются к апдейтеру только через этот файл.

### Что нужно от образа

* Linux с `qemu-guest-agent` и `/bin/sh`.
* Два слота, загрузчик с логикой «пробная загрузка → подтверждение → откат».
* Каталог для записи вне обоих слотов (`scratch_dir`): туда стенд пишет блоки-метки, по которым
  находит нужные моменты в журнале записей диска.
* **Строка загрузчика на последовательной консоли** при каждой загрузке: какой слот выбран и
  на каком состоянии. Без неё не работают проверки блочного уровня (`window`, `reorder`,
  `crash-replay`). Для GRUB это две строки `echo` в `grub.cfg`.

### Поля файла

| Поле | Обязательно | Смысл |
|---|---|---|
| `name`, `description` | да | имя адаптера (совпадает с именем файла) |
| `image` | да | qcow2-образ в исходном состоянии |
| `slots` | нет, `[A, B]` | имена слотов, как их печатает `status` |
| `initial` | да | `{slot, version}` образа до обновления |
| `scratch_dir` | нет, `/data` | каталог для меток, вне обоих слотов |
| `artifacts` | да | роль → `{path, version}`: путь к артефакту в госте и версия, которую `status` покажет после его загрузки |
| `commands.install` | да | установка; `{artifact}` заменяется путём артефакта |
| `commands.status` | да | печатает строки `ключ=значение` (ниже) |
| `commands.reboot` | нет, `systemctl reboot` | перезагрузка |
| `commands.version` | нет | версия апдейтера, записывается в результаты |
| `commands.info` | нет | диагностика конфигурации, записывается в результаты |
| `commands.debug` | нет | подробности для разбора одного состояния (`replay_state.py`) |
| `commands.unconfirm` | для `*-unconfirmed` | вернуть загруженный слот в состояние «загружен, не подтверждён». Без неё эти сценарии получают ERROR |
| `bootlog.run` | для блочного уровня | регулярное выражение строки загрузчика; группа `(?P<slot>)` обязательна, `(?P<order>)` желательна |
| `bootlog.rescue` | нет | строка, которая означает, что следующая загрузка пошла по аварийному правилу |
| `steps`, `variants` | нет | конфигурации образа для экспериментов (ниже) |

### Роли артефактов

| Роль | Что это | Где нужна |
|---|---|---|
| `v1` | корректно подписанная версия образа | `downgrade` |
| `v2` | корректно подписанная новая версия | все сценарии |
| `v2-broken` | корректно подписана, но не загружается (PID 1 завершается) | `broken*` |
| `v2-attacker` | подписана чужим ключом | `attacker` |

Если роли нет, сценарий, которому она нужна, получает ERROR, остальные работают. Изготовление
артефактов пока остаётся за сборочным скриптом образа (для RAUC — `scripts/build_ab_image.py`);
общий интерфейс «драйвера протокола» — задача A2 в `docs/BACKLOG.md`.

**Почему `unconfirm`, а не гонка.** Сценарии `broken-unconfirmed` и `cut-unconfirmed` проверяют
установку, начатую до подтверждения текущей загрузки. Сначала это состояние получали, начиная
установку сразу после ответа агента, наперегонки со службой подтверждения. Исход гонки
не воспроизводится: 31.10 установка успела раньше (откат через аварийное правило), 01.11
служба подтверждения успела раньше, и сценарий выродился в обычный `broken`. Теперь стенд
дожидается подтверждения, вызывает `unconfirm` и проверяет по `status`, что слот действительно
не подтверждён; если нет — вердикт ERROR.

### Вывод `status`

Строки `ключ=значение`, остальные строки игнорируются.

| Ключ | Обязательно | Смысл |
|---|---|---|
| `slot` | да | слот, с которого загружена система |
| `version` | да | версия загруженного ПО |
| `confirmed` | да | `1`, если загрузка этого слота подтверждена и пробная загрузка не висит |
| `env_ok` | для блочного уровня | `1`, если состояние загрузчика читается и корректно. Если ключа нет, стенд не судит и считает `1` |
| `order` | для блочного уровня | порядок загрузки, как его видит ОС, в той же записи, что группа `order` в `bootlog.run`. Расхождение с тем, на что опирался загрузчик, даёт вердикт DEGRADED |
| `primary` | нет | основной слот по мнению апдейтера (диагностика) |
| `env.<имя>` | нет | сырое состояние загрузчика. Сценарий `attacker` проверяет, что оно не изменилось после отклонённой установки |

### Как стенд использует ответы

| Наблюдение | Сценарии |
|---|---|
| `(slot, version)` до и после | все: «установилось», «откатилось», «не тронуто» |
| `confirmed` | ожидание подтверждения перед установкой (как у настоящего агента) и после переключения; проверка, что `unconfirm` сработал |
| `env.*` до и после | `attacker`: отклонённая установка не меняет состояние загрузчика |
| строки `bootlog` | `cut-firstboot`: момент выбора нового слота; блочный уровень: выбор слота, аварийное правило, расхождение `order` |
| `env_ok`, `order` | блочный уровень: DEGRADED при нечитаемом или расходящемся состоянии |

Вердикты блочного уровня: BRICK — не загрузилось; INCONSISTENT — пара `(slot, version)` не равна
ни исходной, ни обновлённой; DEGRADED — загрузилось, но состояние загрузчика нечитаемо,
сработало аварийное правило или загрузчик и ОС видят разный порядок; OK — всё совпало.

### Варианты конфигурации

`steps` — именованные shell-скрипты, `variants` — списки шагов. Шаг выполняется с `set -e` в
загруженном и подтверждённом исходном образе (BIOS, с сетью). Элемент списка — имя шага,
`{step: имя, env: {...}}` с переменными или `{run: "команда"}`. Поле шага `upload:
{путь в госте: путь от bench/}` кладёт файл в гостя перед запуском. `firmware: uefi` запускает
вариант с OVMF.

Готовый вариант кэшируется как оверлей `P:\vm\variants\<адаптер>-<вариант>-<хэш>.qcow2`. Хэш
считается от образа (имя, размер, время изменения) и текста шагов, поэтому после пересборки
образа или правки шага вариант пересоберётся сам.

### Пример: RAUC + GRUB

`bench/updaters/rauc-grub.yaml`: 49 значимых строк без вариантов (10 из них — необязательная
диагностика `info` и `debug`), ещё 113 строк — 13 вариантов
для экспериментов с окном `grubenv`. Главное:

```yaml
artifacts:
  v2: {path: /data/bundles/v2.raucb, version: "2"}
commands:
  install: rauc install {artifact}
  status: |
    S=$(sed -n 's/.*rauc.slot=\([AB]\).*/\1/p' /proc/cmdline)
    L=$(grub-editenv "$E" list 2>/dev/null)
    echo "slot=$S"; echo "version=$(cat /etc/otabench-version)"
    ...
bootlog:
  run: 'otabench-grub: ORDER=\[(?P<order>[^\]]*)\] ... -> (?P<slot>\w)'
```

### Как подключить свой апдейтер

1. Собрать образ с двумя слотами, своим апдейтером и `qemu-guest-agent`; положить в образ
   артефакты ролей `v1`, `v2`, `v2-broken`, `v2-attacker`.
2. Добавить в загрузчик печать выбранного слота на консоль.
3. Написать `bench/updaters/<имя>.yaml`: пути к артефактам, `install`, `status`, `bootlog`.
4. Запустить:
   ```
   bench\.venv\Scripts\python.exe bench\scripts\pilot_ab.py --updater <имя> --only happy
   ```
   Затем остальные сценарии: `broken, attacker, downgrade, cut-firstboot, crash-replay`.

## Совместимость результатов

Результаты пилота, полученные до адаптера v2 (каталоги `results/pilot-ab-*` до 01.11.2026,
17:00), используют старые имена полей: `grub_order` / `linux_order` вместо `boot_order` /
`os_order`, `boot_ab` вместо `device_info`, `rauc_booted` / `rauc_primary` вместо `primary`,
`first_point_booting_B` вместо `first_point_booting_target`. Поля `env_ok`, `diverged`,
`verdict`, `slot`, `version` не менялись. Окно «старое / новое состояние» теперь определяется по
слоту, который выбрал загрузчик, а не по первому элементу `ORDER`; без аварийного правила это
одно и то же. Сценарий `attacker` стал строже: он ждёт подтверждения загрузки, сравнивает
состояние загрузчика до и после установки и перезагружает устройство.
