# Что проверяют существующие тесты, на которые ссылается каталог

Задача D4. Поле `coverage` каталога (`bench/catalog/threats.yaml`) засчитывает угрозу
покрытой, если в существующем наборе есть тест с подходящим именем. Здесь разобрано, что эти
тесты действительно утверждают (исходники: разреженные клоны в `third_party/verify`,
MCUboot `a9767a0`, mendersoftware/integration `b68cbab`, aktualizr `e5118a7`; tuf-conformance
разобран в гл. 1 и `docs/upstream/`). Вывод: покрытие по названиям тестов — оценка сверху,
и у двух тестов MCUboot сами разработчики отметили, что проверка слабее, чем кажется.

## MCUboot: симулятор (`sim/tests/core.rs` → `sim/src/image.rs`)

| Тест | Угроза | Что утверждает | Оговорка |
|---|---|---|---|
| `bad_secondary_slot` → `run_signfail_upgrade` | OTA-AUTH-01 | образ с испорченной подписью во вторичном слоте не устанавливается: трейлеры первичного слота остаются `BOOT_MAGIC_GOOD`, отката нет | проверяется загрузчик, а не доставка |
| `downgrade_prevention` → `run_nodowngrade` | OTA-FRESH-02 | после обычного обновления образ с меньшей версией отклоняется; тест выполняется только при собранной возможности `DowngradePrevention` | в конфигурации без этой возможности тест пропускается |
| `hw_prot_failed_security_cnt_check` → `run_hw_rollback_prot` | OTA-FRESH-02 | аппаратный счётчик безопасности (установлен в 30) не даёт загрузить образ с меньшим счётчиком | только при `HwRollbackProtection` |
| `perm_with_fails` → `run_perm_with_fails` | OTA-PWR-03 | обрыв посередине перманентного обновления: после повторного запуска образы и трейлеры правильные | одна точка «на полпути» |
| `perm_with_random_fails` → `run_perm_with_random_fails(5)` | OTA-PWR-03 | 5 случайных обрывов операций флеш-памяти: первичный слот содержит новый образ | **результат проверки вторичного слота игнорируется** (в коде: «TODO: This result is ignored») |
| `status_write_fails_with_reset` → `run_with_status_fails_with_reset` | OTA-PWR-03 | сбои записи в область статуса со сбросом: обновление доходит до конца, срабатывают предупреждения, а не утверждения | |
| `basic_revert` → `run_basic_revert` | OTA-PWR-04 | откат после неподтверждённого обновления на каждом шаге счётчика возвращает исходные образы | **разработчики отмечают: «this test would also pass if no swap is ever performed»** (FIXME) |
| `revert_with_fails` → `run_revert_with_fails` | OTA-PWR-04 | обрыв в каждой точке отката: откат завершается | перебор точек, как в методике стенда |

## Mender: интеграционные тесты (`tests/tests/`)

| Тест | Угроза | Что утверждает |
|---|---|---|
| `test_unsigned_artifact_fails_deployment` | OTA-AUTH-01 | развёртывание неподписанного артефакта на устройство, требующее подписи, завершается со статусом `finished` и одной неудачей (`failure` = 1) |
| `test_image_download_retry_timeout` | OTA-NET-01 | трафик блокируется после начала загрузки; после снятия блокировки загрузка повторяется и завершается успешно |
| `test_image_download_retry_download_count` | OTA-NET-01 | число неудачных попыток задаётся параметром; при `max_retries ≥ unsuccessful_retries` обновление успешно |
| `test_image_download_retry_hosts_broken` | OTA-NET-01 | хранилище недоступно через `/etc/hosts`; после восстановления развёртывание `finished`, активен новый раздел и установлен новый образ |
| `test_deployed_during_network_outage` | OTA-NET-01 | развёртывание создаётся во время отключения сети; после восстановления — одна успешная установка и ожидаемый образ на устройстве |

Обрыва питания среди этих тестов нет: отказоустойчивость проверяется только по сети.

## aktualizr (`tests/test_io_failure.py`)

| Тест | Угроза | Что утверждает |
|---|---|---|
| `test_io_failure.py` | OTA-NET-01 | цикл подготовки и обновления с **случайными сбоями системных вызовов ввода-вывода** (вероятность по умолчанию 0,00025, 100 прогонов): после неудачной попытки следующий прогон должен довести обновление до конца; при ошибке сохраняется каталог состояния |

Это ближайший к модели стенда тест: сбой вносится в ввод-вывод, а не в сеть. Но это сбой
системного вызова (ошибка возвращается приложению), а не обрыв питания с потерей
несброшенных данных, поэтому к OTA-PWR-* он не отнесён.

## OSS-Fuzz (`projects/rauc`)

`rauc/manifest` и `rauc/bundle` — фаззеры разбора манифеста и бандла RAUC (OTA-PARSE-01):
проверяют отсутствие падений и санитайзерных ошибок, а не семантику проверки.
